# netattrib — сетевая атрибуция с точностью до исполняемого файла для Windows

[English](README.md) | [Русский](README_RU.md)

`netattrib` отвечает на вопрос *«какой исполняемый файл, когда, от имени какого пользователя, с кем
и сколько данных обменялся»* в Windows 10/11 и Windows Server (x64), включая сокеты, которые живут
всего несколько миллисекунд.

Это один статически скомпонованный `.exe` (около 7 МБ) без VC++ Redistributable, .NET и других сред
выполнения. В нём графический интерфейс для исследования «вживую» и консольный режим для скриптов,
аудита и отправки событий в SIEM.

```text
> netattrib --filter-exe winword.exe --dns-events          (пример вывода)
-- 2026-10-21 (UTC)
  TIMESTAMP     PROCESS          PID PATH                              PROTO LOCAL              REMOTE            DOMAIN                     STATE       DIR
? 14:03:22.101Z WINWORD.EXE     4512 C:\Program Files\…\WINWORD.EXE    DNS   -                  52.109.8.21       ecs.office.com             NOERROR     out
+ 14:03:22.123Z WINWORD.EXE     4512 C:\Program Files\…\WINWORD.EXE    TCP4  10.0.0.5:50123     52.109.8.21:443   ecs.office.com             ESTABLISHED out
- 14:03:29.870Z WINWORD.EXE     4512 C:\Program Files\…\WINWORD.EXE    TCP4  10.0.0.5:50123     52.109.8.21:443   ecs.office.com             CLOSED      out
```
(`+` открытие, `~` смена состояния TCP, `-` закрытие, `L` прослушивание, `?` DNS-запрос. Исполняемый
файл Microsoft Word называется `WINWORD.EXE`; на `--filter-exe word.exe` утилита подскажет верное имя.)

## 1. Обзор и возможности

### 1.1 Задача: сетевая атрибуция

Сетевая атрибуция (Process-to-Network correlation) — это сопоставление каждого сетевого соединения
с конкретным процессом: исполняемым файлом, его *экземпляром*, пользователем и родительским
процессом. Обычные инструменты показывают «PID 4512 соединён с 52.109.8.21:443» в момент опроса.
netattrib сообщает больше: это был `WINWORD.EXE`, вот этот экземпляр (PID плюс время создания), от
имени такого-то пользователя; приложение запросило домен `ecs.office.com`; столько-то байт ушло и
пришло; соединение открылось и закрылось тогда-то.

### 1.2 Чем netattrib лучше Resource Monitor и TCPView

TCPView, `netstat` и `Get-NetTCPConnection` получают соединения **периодическим опросом** таблиц
IP Helper: всё, что открылось и закрылось между двумя опросами, для них не существует. Монитор
ресурсов (Resmon) показывает объёмы трафика по процессам и адресам, но его список TCP-подключений —
это текущий снимок, а журнала, экспорта и командной строки у него нет. netattrib получает события
напрямую из ядра через ETW (Event Tracing for Windows) и использует опрос только как страховку.

| | Опрос таблиц (TCPView, netstat) | netattrib |
|---|---|---|
| Кратковременные сокеты | Пропускаются, если короче интервала. **Измерено:** 5 HTTP-соединений по ~50 мс при интервале 5 с не были замечены ни разу | Видны все: connect, accept, send, receive и disconnect — это события ядра `Microsoft-Windows-Kernel-Network` |
| Привязка к процессу | По PID и задним числом: процесс уже мог завершиться, а его PID — достаться другому | По *поколениям* процессов (PID + время создания) из того же потока событий; переиспользованный PID никогда не получит чужое соединение |
| Учёт байтов | Нет (по соединению — только через ESTATS с правами администратора) | Байты отправки и приёма по каждому соединению (режим ETW) |
| Домены | Обратный DNS (PTR), для CDN почти бесполезен | Имя, которое запросило само приложение (DNS-Client ETW); PTR — запасной вариант |
| VPN/TUN с fake-IP (`198.18.0.0/15`) | Виден только фиктивный адрес | Восстанавливается реальный домен |
| История, экспорт, автоматизация | Нет | История закрытых соединений, CSV/JSON, поток JSON Lines для SIEM, консольный режим |

**Накладные расходы низкие:** ненужные события отбрасываются ещё в ядре (маски ключевых слов и
список разрешённых идентификаторов событий), а на горячем пути нет ни выделений памяти, ни работы со
строками, ни системных вызовов. Измерено на машине разработки (24 логических процессора, ~140
TCP-соединений, режим опроса каждые 250 мс): **0,62 % одного ядра, то есть 0,026 % всей машины**,
рабочий набор 10 МБ. Потребление CPU в режиме ETW пока не измерялось (§7.4).

### 1.3 Возможности кратко

* **Захват:** собственная ETW-сессия реального времени (Kernel-Network, Kernel-Process, DNS-Client)
  плюс сверка с таблицами IP Helper; без прав администратора — автоматический переход на опрос.
* **Атрибуция:** путь, пользователь и SID, родительский процесс, службы внутри `svchost`,
  SHA-256 образа, проверка цифровой подписи Authenticode.
* **Домены:** имя, разрешённое самим приложением; обратный DNS как запасной вариант; работа с
  fake-IP прокси-клиентов (v2rayN, Xray, sing-box).
* **Графический интерфейс:** дерево процессов, таблица соединений с фильтрами в стиле Excel,
  контекстные меню (Проводник, VirusTotal, разрыв соединения, завершение процесса), предупреждения
  о неподписанных процессах, выходящих в интернет.
* **Консоль и SIEM:** живая таблица, сводка по исполняемым файлам, CSV, JSON Lines, агрегаты по
  интервалам, итоговая сводка при выходе.
* **Безопасный запуск с правами администратора:** защита от подмены DLL, Control Flow Guard,
  аппаратный теневой стек Intel CET (§3).

## 2. Графический интерфейс (GUI)

Запуск без аргументов (например, двойным щелчком в Проводнике) открывает окно; то же делает
`netattrib --gui`. Интерфейс построен на egui/eframe (OpenGL) и устроен как вкладка «Сеть»
Монитора ресурсов рядом с деревом процессов Process Explorer. Окно работает на том же движке
захвата, что и консольные режимы.

Для полного захвата (кратковременные сокеты, байты, домены из DNS-Client) запускайте от имени
администратора. Без прав окно работает в режиме опроса; кнопка *Restart as administrator*
перезапускает его через UAC с теми же аргументами.

### 2.1 Верхняя панель

Слева — переключатели и действия, справа — состояние захвата.

* **Hide background noise** («Скрыть фоновый шум», включено по умолчанию) скрывает многоадресный
  и широковещательный трафик, служебные порты обнаружения в локальной сети (NetBIOS 137/138, SSDP
  1900, mDNS 5353, LLMNR 5355) и **самозацикленный loopback** — процесс, соединённый сам с собой
  через 127.0.0.1 (так постоянно делает `esrv_svc.exe` от Intel). Loopback между *разными*
  процессами, например `steam.exe` → `xray.exe` через локальный прокси, не скрывается никогда:
  именно по нему видно, куда приложение отправляет трафик.
* **Keep closed history** («Хранить историю закрытых», включено по умолчанию) оставляет закрытые
  соединения в таблице, до 2000 последних. Если выключить, они исчезают через 10 с после закрытия.
  *Clear history* очищает историю сразу.
* **Export…** сохраняет строки, видимые в таблице (с учётом фильтров и сортировки), в CSV или
  массив JSON через стандартный диалог сохранения. Имена полей совпадают с §8; байты сырые;
  `state` — отображаемое состояние, `tcp_state` — состояние сокета; `peer_process`/`peer_pid` —
  второй конец loopback-соединения; `signature` (`signed`/`unsigned`/`invalid`) и `signer` —
  подпись образа процесса.
* **Clear filters** появляется, пока отфильтрован хотя бы один столбец, и снимает все фильтры
  столбцов.
* **Индикатор состояния:** *ETW capture active* (зелёный) или *Polling only* (жёлтый), плюс
  уровень прав. Подсказка объясняет, почему ETW недоступен, и показывает, где хранятся
  настройки. Если окно слишком узкое, индикатор переносится на отдельную строку.

### 2.2 Дерево процессов

* Дерево строится по связи **родитель → потомок (PPID → PID)** и упорядочено по времени создания.
  Родитель обязан быть старше потомка, поэтому переиспользованный PPID никогда не «усыновит» чужие
  процессы.
* **Активные сетевые узлы подсвечены:** процессы с активными соединениями выделены зелёным и
  показывают их число; свёрнутые узлы показывают `+N` — соединения в дочерних процессах.
* **All / User / System** ограничивают дерево *и* таблицу по учётной записи процесса. *User* —
  SID текущего пользователя; *System* — SYSTEM, LOCAL/NETWORK SERVICE, учётные записи служб, DWM и
  драйверов шрифтов. Если токен прочитать нельзя, процесс в сеансе 0 считается системным. В режиме
  *User* системные родители пользовательских процессов остаются видимыми (приглушённо), чтобы не
  терялась иерархия.
* **Поиск процесса** (Ctrl+F, крестик `×` внутри поля очищает его) ищет по имени, имени службы или
  точному PID. Он обрезает дерево до совпадений, их родителей и потомков, подсвечивает их и
  прокручивает к ним, но таблицу не меняет. Таблицу меняет только щелчок по процессу: показываются
  он **и все его потомки**; повторный щелчок или `×` снимает выбор.
* *Only with connections* скрывает процессы без соединений; `+`/`−` раскрывают и сворачивают всё.

### 2.3 Таблица соединений

Столбцы: Process · PID · Local Address · Remote Address · Domain · Proto · State · Sent · Recv.

* Объёмы показываются в Б/КБ/МБ/ГБ, а прочерк `—` означает, что байты не считаются (режим опроса
  или TCP с `--no-bytes`).
* **Домен** берётся сначала из кэша DNS-Client: это имя, которое запросило приложение. Обратный DNS
  — запасной вариант.
* Строки с трафиком за последние 2 с выделены жирным; закрытые соединения показывают красное
  `CLOSED`. Щелчок по заголовку сортирует.

### 2.4 Столбцы как в электронной таблице

* **Независимое изменение ширины:** перетаскивание правой границы меняет ширину только этого
  столбца, последующие столбцы сдвигаются, а когда перестают помещаться, появляется горизонтальная
  прокрутка.
* **Автоподбор ширины по двойному щелчку** по заголовку или правой границе столбца: ширина
  подгоняется под самый широкий из заголовка и значений во *всех* строках, оставшихся после
  фильтров, а не только видимых на экране. (Первый щелчок двойного щелчка пересортировал бы
  таблицу — это отменяется.)
* Ширина по умолчанию / минимальная: Process 140/60 пикселей, PID 65/45, Local и Remote Address
  150/70, Domain 200/90, Proto 60/40, State 90/50, Sent и Recv 75/50.
* Значения сами по себе столбец не расширяют — длинные обрезаются: столбец, растущий вслед за
  самым длинным значением, сдвигал бы все столбцы правее. Слишком длинные заголовки заканчиваются
  на `…`. Ширины столбцов сохраняются между запусками.

### 2.5 Фильтры столбцов в стиле Excel (AutoFilter)

* У каждого заголовка справа есть кнопка-воронка: серая, пока столбец не отфильтрован, и голубая,
  когда фильтр активен. Щелчок по ней открывает всплывающее окно и **не** сортирует таблицу.
* **Текстовый поиск** *Contains…* — подстрока без учёта регистра в том, что показывает столбец;
  применяется сразу при вводе. Например, `microsoft` в столбце Domain оставит только подходящие
  домены.
* **Список уникальных значений с флажками** и числом строк для каждого (пустые значения —
  *(Blanks)* — в конце), флажок *(Select All)* сверху и кнопка *Clear Filter* снизу. Особенно
  удобно для Proto (`TCP4`, `UDP4`, `TCP6`), State (`ESTABLISHED`, `CLOSED`, `PROXY/LOCAL`,
  `LOCAL/IN`) и Process.
* Как в Excel, список столбца показывает значения, оставшиеся после фильтров на *других*
  столбцах, а фильтры нескольких столбцов объединяются по «И».
* **Данные «живые»**, поэтому выбор определяет и судьбу новых значений. Если снять несколько
  флажков, новые значения продолжают появляться. Если снять *(Select All)* и отметить несколько
  значений, ничего другого не появится.
* У Sent и Recv списка нет (объёмы слишком разнообразны) — только поиск. Пока отфильтрован хотя
  бы один столбец, строка состояния перечисляет такие столбцы. Фильтры действуют до конца сеанса,
  а *Export…* сохраняет то, что они оставили.

### 2.6 Контекстные меню

**Процесс в дереве** (правая кнопка мыши):

* *Open file location* — открыть Проводник с выделенным файлом.
* *Copy executable path*, *Copy PID*.
* *Check Executable Hash on VirusTotal* — вычисляет SHA-256 образа (в фоне, если `--hash` ещё не
  сделал этого) и открывает отчёт VirusTotal в браузере. С машины уходит только хеш в составе
  URL; сам файл никуда не загружается.
* *Terminate process…* — с подтверждением. Отказывает, если PID уже принадлежит другому процессу
  (проверяется время создания), и отказывает для критических системных процессов, завершение
  которых обрушило бы Windows.

**Строка таблицы:**

* *Copy remote IP:port*, *Copy resolved domain*, *Copy row*.
* *Look up … on VirusTotal* для IP-адреса или домена (репутация, пассивный DNS, WHOIS). Проверка
  IP предлагается только для публичных адресов, но не для частных, loopback или fake-IP.
* *Show only …* — оставить в таблице процесс этой строки или процесс на другом конце
  loopback-соединения.
* *Close Connection* — **принудительный разрыв сокета** через `SetTcpEntry` с
  `MIB_TCP_STATE_DELETE_TCB`, как в System Informer: соединение удаляется, удалённой стороне
  отправляется сброс. Приложение может просто переподключиться. Требуются права администратора;
  для IPv6 и UDP в Windows такого API нет, поэтому в этих случаях (и для закрытых строк) пункт
  недоступен, а причина видна в подсказке.

Меню остаётся привязанным к строке, на которой его открыли, даже если таблица тем временем
пересортировалась.

### 2.7 Цифровые подписи

* Подпись Authenticode каждого образа проверяется в фоне (около 14 мс на уникальный файл; 144
  образа — 2 с). Файл без встроенной подписи ищется в системных каталогах безопасности, где
  подписано большинство файлов Windows. Приложение из пакета MSIX/Store получает статус, который
  Windows проверила при установке пакета.
* Проверка выполняется офлайн: без проверки отзыва сертификатов и без их загрузки (netattrib не
  создаёт собственного трафика).
* Процесс с **неподписанным** образом (жёлтый) или с **недействительной** подписью (красный:
  файл изменён после подписания, сертификат отозван, недоверенный корень…), который обращается к
  публичному адресу в интернете, получает значок-предупреждение в дереве и треугольник перед именем
  в соответствующих строках таблицы. Подсказка процесса показывает *Signed by …* (с пометкой
  *catalog* или *app package*), *Not signed* или причину недействительности.

### 2.8 Локальные прокси, loopback и фиктивные адреса VPN/TUN

* **Системный прокси** (v2rayN, Clash и подобные в режиме «System Proxy»): единственные сокеты
  приложения ведут на `127.0.0.1:<порт>`. netattrib сопоставляет оба конца каждого
  loopback-соединения. Строка приложения получает состояние `PROXY/LOCAL` и в столбце Domain —
  *via xray.exe (64056)*, процесс-владелец порта. Принимающий конец прокси показывает `LOCAL/IN` и
  *from steam.exe (4512)*. Собственные исходящие соединения прокси показывают, куда трафик ушёл на
  самом деле. В GUI loopback захватывается всегда.
* **TUN-режим с fake-IP:** DNS-ответы прокси-клиента — фиктивные адреса из `198.18.0.0/15`.
  netattrib восстанавливает для них **реальные домены** через кэш DNS-Client ETW: ответ, который
  получило приложение, привязывается к паре (IP, PID), поэтому следующее соединение подписывается
  доменом, который запросило именно это приложение (подробно — §7.6).

### 2.9 Настройки и портативный режим

* Между запусками сохраняются положение, размер и развёрнутость окна, ширина панели процессов,
  ширины столбцов таблицы, *Hide background noise*, *Keep closed history*, *Only with connections*
  и выбор *All / User / System*. Файл настроек — `%APPDATA%\netattrib\data\app.ron`.
* **Портативный режим**, как в System Informer: создайте пустой файл `netattrib.settings.ron`
  рядом с `netattrib.exe`, и настройки будут храниться в нём, а в профиль ничего записываться не
  будет.
* *Restart as administrator* сначала сохраняет настройки, поэтому окно с правами администратора
  открывается в том же виде.

Окно раз в секунду снимает данные с движка в фоновом потоке (`gui-sampler`) и отображает неизменяемый
снимок, поэтому интерфейс никогда не удерживает блокировку, нужную потребителю ETW. `--log` и
`--summary` работают одновременно с окном, включая итоговые записи закрытия `shutdown`. При запуске
из Проводника консоль, выделенная процессу, освобождается; при запуске из терминала консоль
остаётся для диагностики, а Ctrl+C в ней закрывает окно.

## 3. Безопасность и надёжность

netattrib рассчитан на запуск с правами администратора и часто запускается прямо из папки, куда
был скачан. Поэтому он защищён от атак, типичных для повышенных прав.

### 3.1 Защита от подмены DLL и исполняемых файлов

Windows ищет DLL программы **сначала в её собственной папке**. До исправления пустышка `tdh.dll`,
положенная рядом с `netattrib.exe`, загружалась вместо системной (процесс падал с `0xC0000139`), то
есть вредоносная DLL рядом с файлом выполнилась бы с правами администратора. Стандартный
`std::process::Command` в Rust точно так же ищет программу по короткому имени: подложенный
`explorer.exe` запускался, когда GUI открывал URL или Проводник.

* **Импортируемые DLL:** компоновка с `/DEPENDENTLOADFLAG:0x800`
  (`LOAD_LIBRARY_SEARCH_SYSTEM32`, см. `.cargo/config.toml`), как у System Informer. Загрузчик
  берёт `tdh`, `iphlpapi`, `wintrust`, `opengl32` и остальные только из System32. Проверено: с
  подложенными рядом `tdh.dll`, `wintrust.dll` и `iphlpapi.dll` релизная сборка работает нормально.
* **DLL, загружаемые во время работы:** первым вызовом в `main()` выполняется
  `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`.
* **Проводник и браузер** запускаются как `%SystemRoot%\explorer.exe` по абсолютному пути.

### 3.2 Защита от эксплуатации уязвимостей

* **Control Flow Guard (CFG):** проверка косвенных вызовов в коде netattrib и его зависимостей
  (`-C control-flow-guard=checks`; предсобранная стандартная библиотека не инструментирована).
* **Intel CET (`/CETCOMPAT`):** аппаратный теневой стек защищает адреса возврата на процессорах с
  поддержкой CET (x64). `Get-ProcessMitigation` показывает *UserShadowStack: ON* для запущенного
  GUI.
* Плюс стандартные механизмы: ASLR с высокой энтропией и DEP. `dumpbin` показывает *Control Flow
  Guard* и *CET compatible*.
* **Манифест** (`build.rs`): `asInvoker` (эвристика установщиков никогда не повысит права
  автоматически), Common Controls 6, `supportedOS` для Windows 10/11, `longPathAware`.

### 3.3 Де-элевация браузера и Проводника

Даже когда netattrib работает с правами администратора, ссылки VirusTotal и *Open file location*
не открываются с повышенными правами. Запрос передаётся `explorer.exe`, а тот отдаёт его уже
запущенной оболочке пользователя, поэтому браузер и окно Проводника работают с обычными правами.
Дочерним процессам не передаются стандартные дескрипторы (иначе после освобождения консоли запуск
падал с ошибкой «os error 6», `ERROR_INVALID_HANDLE`).

### 3.4 Надёжность

* **Защита от переиспользования PID:** процесс всегда идентифицируется парой (PID, время создания);
  то же касается фильтров и завершения процессов (§7.1).
* **Ограниченная память и очереди:** ETW-буферы 4–32 МБ, очередь вывода 65 536 записей, кэши DNS
  до 100 тыс. записей; медленный приёмник приводит к учитываемым потерям записей, но не к потере
  ETW-буферов (§7.4).
* **Корректное завершение:** собственная ETW-сессия `NetAttrib-<pid>` останавливается при выходе,
  Ctrl+C, закрытии консоли или аварийном завершении; «осиротевшие» сессии от убитых процессов
  убираются при следующем запуске.
* **Отказ в доступе никогда не фатален:** каждое поле деградирует отдельно и становится `null`.

## 4. Консольный режим (CLI)

```text
netattrib [--gui | --no-gui]
          [--filter-exe NAME]... [--filter-pid PID]... [--filter-path GLOB]... [--tree]
          [--group] [--json-lines | --csv] [-o FILE] [--log FILE] [--summary FILE]
          [--dns-events] [--hash] [--listening] [--include-loopback] [--no-bytes]
          [--no-etw] [--poll-ms MS] [--no-rdns] [--dns-wait-ms MS] [--duration SECS] ...
```

| Задача | Команда |
|---|---|
| **Графический интерфейс** (по умолчанию без аргументов) | `netattrib` или `netattrib --gui` |
| …только Word и его потомки, с журналом JSONL | `netattrib --gui -e winword --tree --log C:\logs\net.jsonl` |
| Живая консольная таблица всех соединений | `netattrib --no-gui` |
| **Режим A**: соединения Word вживую | `netattrib --filter-exe winword.exe` |
| …с дочерними процессами и DNS-запросами | `netattrib -e winword --tree --dns-events` |
| …один конкретный экземпляр | `netattrib --filter-pid 4512` |
| …всё из каталога Office | `netattrib --filter-path "*\Microsoft Office\*"` |
| **Режим B**: живая сводка по исполняемым файлам | `netattrib --group` (`--sort tx\|rx\|conns\|remotes\|name`) |
| SIEM: поток событий | `netattrib --json-lines -o C:\logs\net.jsonl` или `… \| ваш-шиппер` |
| SIEM: агрегаты каждые 60 с + полная сводка при выходе | `netattrib --group --json-lines --interval 60000` |
| Консольная сводка **и** журнал JSONL одновременно | `netattrib --group --log C:\logs\net.jsonl --summary C:\logs\summary.jsonl` |
| Инвентаризация за 10 минут в CSV | `netattrib --csv --duration 600 -o inventory.csv` |
| Включить прослушивающие и привязанные UDP-сокеты | `--listening` |
| Word за локальным системным прокси (`127.0.0.1:10808`) | `netattrib -e winword` (с любым фильтром процессов loopback включается) |
| Loopback в нефильтрованном консольном запуске | `--include-loopback` |

Примеры для скриптов:

```powershell
# Минутный захват всех соединений в CSV (для отчёта или Excel)
netattrib --csv --duration 60 -o conns.csv

# Поток событий в JSON Lines и их разбор в PowerShell
netattrib --json-lines --duration 30 -o net.jsonl
Get-Content net.jsonl | ConvertFrom-Json | Where-Object event -eq 'open' |
    Group-Object process | Sort-Object Count -Descending

# Что делает конкретная программа вместе с дочерними процессами и её DNS-запросы
netattrib --no-gui -e setup.exe --tree --dns-events --log C:\logs\setup.jsonl
```

**Режим B (TUI):** верхняя панель — исполняемые файлы (PIDS, ACT — активные, TOTAL — всего
соединений, RMT — уникальные удалённые адреса, TX/RX, USER, DESTINATIONS, сгруппированные по
доменам, PATH). Нижняя панель — живые соединения, самые свежие сверху; строки с трафиком за
последние 2 с подсвечены. Размер окна перечитывается каждый кадр. Ctrl+C завершает работу; после
закрытия альтернативного экрана печатается текстовая сводка.

**Потоковая таблица:** столбцы подстраиваются под ширину окна; на узких терминалах первыми
убираются менее важные (TX/RX, DIR, PATH, LOCAL, DOMAIN), строки никогда не переносятся. Время в
таблице — `HH:MM:SS.mmmZ` (UTC) под баннером с датой; в экспорте — полный ISO-8601 UTC с
микросекундами.

Состояние и диагностика всегда идут в **stderr**, поэтому stdout остаётся чистым для конвейеров.

## 5. Сборка, запуск и системные требования

### 5.1 Системные требования

* Windows 10/11 или Windows Server, x64.
* **Права администратора** — для захвата через ETW (кратковременные сокеты, байты, домены
  DNS-Client); в этом случае автоматически включается `SeDebugPrivilege`, чтобы определять
  владельцев процессов других пользователей и SYSTEM. Альтернатива — группа *Performance Log
  Users*: `net localgroup "Performance Log Users" <пользователь> /add` (затем выйти и войти);
  владельцы чужих процессов тогда определяются ограниченно.
* Без прав netattrib работает в режиме опроса и сообщает об этом.

| Данные | Администратор | Обычный пользователь |
|---|---|---|
| Захват ETW (кратковременные сокеты, байты, домены) | ✔ | ✘ → автоматический переход на опрос с предупреждением |
| PID владельца каждого TCP/UDP-сокета | ✔ | ✔ (IP Helper) |
| Полный путь к образу любого процесса, включая SYSTEM/PPL | ✔ | ✔ через `SystemProcessIdInformation` |
| Владелец процесса (пользователь/SID токена) | ✔ почти для всех | Только свои процессы; для остальных `user: null` |
| SHA-256 образа (`--hash` или по запросу в GUI) | ✔ | ✔, если файл читается |
| Подпись Authenticode образа (GUI) | ✔ | ✔, если файл читается |
| *Close Connection* (GUI, IPv4 TCP) | ✔ | ✘ (пункт меню недоступен) |

### 5.2 Готовая сборка

Скачайте `netattrib-v<версия>-windows-x64.zip` со страницы
[Releases](https://github.com/mangoost-sec/netattrib/releases) и проверьте контрольную сумму:

```powershell
(Get-FileHash .\netattrib-v1.0.0-windows-x64.zip -Algorithm SHA256).Hash
Get-Content .\netattrib-v1.0.0-windows-x64.zip.sha256
```

Хеши должны совпасть (регистр букв не важен).

### 5.3 Сборка из исходников

* Rust **1.95+** с набором инструментов MSVC: `rustup default stable-x86_64-pc-windows-msvc`
  (версия 1.95 нужна egui/eframe 0.37, на которых построен GUI).
* Visual Studio Build Tools с рабочей нагрузкой «Разработка классических приложений на C++»
  (включает Windows SDK: компоновщик MSVC и `rc.exe`, которым `build.rs` встраивает иконку,
  сведения о версии и манифест).

```powershell
cargo build --release          # -> target\release\netattrib.exe (статический CRT, без зависимостей)
cargo test                     # модульные тесты
powershell -ExecutionPolicy Bypass -File scripts\package-release.ps1   # zip + SHA-256 в dist\
```

Профиль релиза: `opt-level = 3`, полный LTO, одна единица кодогенерации, удалённые символы,
`panic = "abort"`. Измерено на этом проекте: thin LTO давал exe **на 6 % больше**, поэтому оставлен
полный LTO; `abort` даёт exe **на 20 % меньше**, чем `unwind`. Обработчик паники всё равно
останавливает ETW-сессию, а в GUI показывает ошибку в окне сообщения. Флаги защиты
(`/DEPENDENTLOADFLAG:0x800`, CFG, `/CETCOMPAT`) задаются в `.cargo/config.toml` и применяются к
любой сборке.

### 5.4 Запуск

* **Рекомендуется командная строка с правами администратора.** Включаются захват ETW и
  `SeDebugPrivilege`.
* Каждый запуск использует собственную ETW-сессию `NetAttrib-<pid>`. Сессия, оставшаяся после
  принудительно завершённого процесса, убирается при следующем запуске; вручную:
  `logman stop NetAttrib-<pid> -ets`.
* **Самопроверка ETW** (с правами администратора):
  `powershell -ExecutionPolicy Bypass -File scripts\etw-selftest.ps1`. Скрипт прогоняет дочерний
  процесс через разрешение DNS и пять коротких HTTP-соединений, пока намеренно агрессивный опрос
  каждые 250 мс соревнуется с доставкой ETW, и проверяет захват, источник событий, ровно одно
  открытие и одно закрытие на сокет, направление, байты, атрибуцию и сопоставление DNS. Результат
  записывается в `selftest-result.txt`.

## 6. Как это устроено

### 6.1 Почему Rust

* **Доступ к нативным API без среды выполнения.** `windows-sys` даёт прямые привязки к ETW, TDH,
  IP Helper, CNG и диспетчеру служб; итог — один статически скомпонованный `.exe`.
* **Никакой сборки мусора в обратном вызове ETW.** Потребитель реального времени, который
  притормаживает, теряет буферы ядра (`RealTimeBuffersLost`). В Rust нет пауз сборщика мусора.
* **Безопасность там, где это важно.** Весь `unsafe` ограничен маршалингом FFI; конечный автомат,
  фильтрация и вывод — безопасный код, покрытый модульными тестами.

### 6.2 Источники телеметрии

| Источник | Для чего | Почему |
|---|---|---|
| `Microsoft-Windows-Kernel-Network` (ETW) | Жизненный цикл сокетов и байты, PID владельца | Событийный; полезная нагрузка v0 неизменна со времён Vista и декодируется по фиксированным смещениям |
| `Microsoft-Windows-Kernel-Process` (ETW) | Запуск/остановка процессов → поколения PID | Тот же поток и те же часы, что у сетевых событий; это и делает задачу переиспользования PID решаемой |
| `Microsoft-Windows-DNS-Client` (ETW, событие 3008) | Имя ↔ IP так, как его разрешило **приложение**; аудит DNS по процессам | Записи PTR для CDN бесполезны; важно запрошенное имя |
| `GetExtendedTcpTable/UdpTable` | Точные состояния TCP, уже существующие соединения, прослушивание, запасной режим | Дёшево (≈110 мкс на обе таблицы TCP) и без прав; при активном ETW только сверяет (раз в 5 с) и никогда не опережает ETW (§7.5) |
| `NtQuerySystemInformation` | Снимок процессов с временем создания; путь к образу любого PID без дескриптора | Работает через границы прав |

Отклонено: единственный *NT Kernel Logger* (конфликтует с Procmon, System Informer и WPR — netattrib
запускает собственную сессию), выноски WFP (нужен подписанный драйвер) и захват пакетов (в нём нет
PID).

### 6.3 Архитектура и поток данных

```text
                ┌──────────────────────── kernel ───────────────────────────────┐
                │ Kernel-Network  Kernel-Process  DNS-Client        TCP/UDP tables│
                │   (keyword + event-ID allow-list filters applied in-kernel)     │
                └──────┬──────────────────────────────────────────────┬──────────┘
                 ETW real-time session "NetAttrib-<pid>"              │ GetExtendedTcp/UdpTable
                 128 KB buffers, 32–256 (×CPU above 64), 1 s flush    │ ETW: every 5 s, after a forced flush
                 (+ EVENT_TRACE_CONTROL_FLUSH before every poll)      │ (1 s while ETW reports losses)
                                                                      │ poll-only: every 250 ms
                       │                                              │
            ┌──────────▼──────────┐                         ┌─────────▼──────────┐
            │ etw-consumer thread │  fixed-offset decode    │   poller thread    │ + process snapshot
            │ (ProcessTrace cb)   │  TDH for process/DNS    │                    │   only when a new
            └──────────┬──────────┘                         └─────────┬──────────┘   socket appears
                       │ NetEvent / Seed / DnsAnswer                  │ rows (t1 = read time)
                       ▼                                              ▼
            ┌────────────────────────────── Engine (one Mutex) ────────────────────────────┐
            │ ProcessTable: pid → [generation(create_time, exit_time, path, filter verdict)] │
            │ flows: (proto, local, remote) → state, dir, bytes, owner                       │
            │ pending: events whose PID is not yet known (≤1.5 s, reorder tolerance)         │
            │ confirmation window: poll-found sockets wait ≤3 s for ETW before open/close    │
            │ tombstones: closed tuples (suppress teardown echoes)                           │
            │ per-exe aggregates: pids, active/total, remotes, DNS names, bytes              │
            └───────┬──────────────────────────────┬───────────────────────────┬────────────┘
                    │ outbox → try_send (bounded,   │ snapshot()                │ enrich queue
                    │ drops counted, never blocks)  │                           ▼
                    ▼                               ▼                 ┌────────────────────┐
         ┌──────────────────────┐       ┌──────────────────────┐      │ enrich thread      │
         │ writer thread        │       │ Mode B renderer      │      │ token user + SID,  │
         │ order-preserving     │       │ (main thread, 1 Hz,  │      │ account (LSA)      │
         │ hold ≤ --dns-wait-ms │       │ alt screen, resize-  │      │ → enrich-files:    │
         │ → table | JSONL | CSV│       │ safe)                │      │ SHA-256, signature │
         │ → --log JSONL        │       └──────────┬───────────┘      └────────────────────┘
         └──────────┬───────────┘                  │
                    └───────────► Dns cache ◄───────┘   passive (DNS-Client, keyed by ip+pid, 1 h)
                                     │                  PTR (positive 1 h / negative 10 min)
                                     └─► rdns-0..3 workers (bounded queue 4096, in-flight dedupe)
```

В GUI вместо писателя и рендерера режима B работают поток `gui-feed` (история закрытых соединений)
и поток `gui-sampler` (снимок раз в секунду).

**Записи** (поле `event`): `open` · `state` · `close` (`reason`: `disconnect` | `gone` | `idle` |
`shutdown`, с итоговыми счётчиками байтов) · `listen` · `dns`. Режим B выдаёт записи `aggregate` за
интервал (только изменившиеся исполняемые файлы) и `summary` при выходе.

| `src/console.rs`, `src/win.rs` | Режим VT, размер окна, Ctrl+C и закрытие окна, повышение прав, `SeDebugPrivilege`, ограничение поиска DLL |
| `src/gui/` | Окно, дерево, таблица, значки подписей (`mod.rs`); фоновый сэмплер и PID-безопасное построение дерева (`snapshot.rs`); экспорт CSV/JSON (`export.rs`); фильтры столбцов в стиле Excel (`autofilter.rs`); настройки и портативный режим (`settings.rs`); освобождение консоли, диалог сохранения, перезапуск через UAC, Проводник по абсолютному пути, завершение процессов, разрыв соединений `SetTcpEntry` (`native.rs`) |

## 7. Пограничные случаи

### 7.1 Гонка переиспользования PID

Windows отдаёт PID новому процессу сразу после закрытия последнего дескриптора завершившегося.
netattrib никогда не считает PID идентичностью:

1. **Поколения.** Каждый процесс — это пара `(pid, create_time)`. Стартовый снимок, события ETW
   ProcessStart/Stop и (в режиме опроса) снимки после опроса поддерживают отсортированный список
   поколений для каждого PID. Сетевое событие в момент *T* привязывается к поколению с
   `create_time ≤ T`, которое не завершилось до *T*.
2. **Терпимость к переупорядочиванию.** ETW реального времени доставляет буферы процессоров не по
   порядку, и событие сокета может прийти раньше события запуска процесса. События с неизвестным
   PID ждут до 1,5 с (байты продолжают накапливаться) и отпускаются, как только приходит нужный
   ProcessStart.
3. **Проверка по требованию.** Если PID всё ещё неизвестен, процесс открывается и его
   `GetProcessTimes` сравнивается со временем события. Процесс, **созданный после события**, — это
   переиспользованный PID, и он никогда не обвиняется; событие получает
   `"attribution":"exited"`.
4. **Режим опроса.** Таблицы читаются в момент *t1*, а снимок процессов делается *после* *t1*,
   поэтому экземпляр, созданный позже *t1*, не может оказаться владельцем из таблицы.
5. **Фильтры и обогащение привязаны к экземпляру.** `--filter-pid 4512` закрепляет экземпляр,
   живой на момент запуска; процесс, позже получивший тот же PID, под фильтр не попадёт. Перед
   чтением токена время создания проверяется повторно.

### 7.2 Задержка разрешения DNS

* Потоки захвата ничего не разрешают: обратный вызов ETW только записывает ответы DNS-Client.
* Запросы PTR выполняют 4 рабочих потока за **ограниченной** очередью (4096); одинаковые
  запросы объединяются, при переполнении запрос отбрасывается (и учитывается), а не блокирует.
* Кэши: пассивные имена — 1 ч с ключом `(ip, pid)`, поэтому два приложения, обращающиеся к одному
  IP CDN, сохраняют свои имена; результаты PTR — 1 ч при успехе и 10 мин при неудаче; оба кэша до
  100 тыс. записей.
* Писатель может удерживать записи **в порядке поступления** не дольше `--dns-wait-ms` (по
  умолчанию 400 мс), пока выполняется PTR-запрос, — тогда домен попадает уже в строку `open`.

### 7.3 Границы прав

Таблица — в §5.1. Отказ в доступе никогда не фатален: каждое поле деградирует отдельно и в
экспорте становится `null`.

### 7.4 Ресурсы (цель — менее 1 % CPU)

* **Отсев в ядре.** Маски ключевых слов и список разрешённых идентификаторов событий
  (`EVENT_FILTER_TYPE_EVENT_ID`): TCPCopy (двойной учёт байтов) и события неудачного соединения не
  покидают ядро. `--no-bytes` дополнительно отбрасывает посегментные события отправки/приёма TCP.
* **Горячий путь.** Для пакета известного потока — декодирование по фиксированным смещениям, один
  поиск в хеш-таблице и увеличение счётчиков; без выделения памяти, строк и системных вызовов.
* **Дисциплина блокировок.** Один мьютекс на микросекунды; записи отправляются после разблокировки
  через `try_send`, поэтому медленная консоль или канал вызывают учитываемые потери записей, но
  никогда — потерю ETW-буферов.
* **Ограниченная память.** ETW-буферы 128 КБ × 32–256 (4–32 МБ; больше только при более чем 64
  логических процессорах), поток-потребитель с повышенным приоритетом; очередь вывода 65 536
  записей, отложенные события до 50 тыс., до 4096 удалённых адресов на исполняемый файл, кэши DNS
  до 100 тыс.; завершившиеся процессы удаляются через 2 мин, когда на них никто не ссылается.
* **Режим только опроса.** Снимок процессов стоит ≈5,4 мс, поэтому делается только когда новый
  сокет нужно атрибутировать (плюс раз в 5 с для учёта).

Измерено на машине разработки (24 логических процессора, ~140 TCP-соединений, без прав, опрос
250 мс, `--group --json-lines`): **0,62 % одного ядра = 0,026 % машины**, рабочий набор 10 МБ. До
оптимизации «снимок по требованию» тот же запуск занимал 5,1 % ядра. CPU в режиме ETW пока не
измерялся.

### 7.5 Гонка опроса и ETW: один сокет — одно `open` и одно `close`

ETW реального времени доставляет буферы при заполнении или по таймеру сессии (минимум 1 с, и
netattrib его уже использует). Опрос таблиц — мгновенный снимок, поэтому он может увидеть сокет
*раньше*, чем будет доставлено его событие Connect. Движок устраняет дубли:

1. **Окно подтверждения.** В режиме ETW сокет, впервые найденный опросом, отслеживается сразу, но
   его запись `open` задерживается до 3 с.
2. **Повышение.** Любое событие Kernel-Network для такого потока помечает его `source: etw` и сразу
   объявляет с временем начала из ETW и точным направлением (Connect → `out`, Accept → `in`). Если
   за окно ничего не пришло, поток объявляется как `poll`.
3. **Зеркальный случай для закрытий.** Сокет, исчезнувший из таблицы, закрывается как `gone`,
   только если ETW не закрыл его за то же окно; иначе запоздавшие Disconnect и байты потерялись бы.
4. **Порядок сохраняется.** Поток, закрывшийся внутри окна, всё равно выдаёт `open` раньше
   `close`.
5. **Свежее состояние ETW перед каждым опросом** (`EVENT_TRACE_CONTROL_FLUSH`).
6. **Опрос как страховка.** При активном ETW опрос идёт раз в 5 с; если сессия сообщает о потерях
   в ядре, опрос учащается до 1 с на 60 с с предупреждением. `--poll-ms` переопределяет интервал.

### 7.6 TUN-прокси и фиктивные адреса (v2rayN / Xray / sing-box)

Прокси-клиенты в режиме TUN обычно используют DNS в режиме **fake-IP**: каждый ответ — синтетический
адрес из `198.18.0.0/15` (диапазон для тестирования сетей, RFC 2544, в интернете не
маршрутизируется). Ядро прокси помнит соответствие fake-IP → домен, перехватывает соединение
приложения через виртуальный адаптер и открывает собственное соединение с прокси-сервером. Что
видит netattrib:

* **Сокет приложения** ведёт на фиктивный адрес и верно приписан приложению, например
  `powershell.exe → 198.18.0.17:80` в самопроверке.
* **Исходящее соединение** принадлежит ядру прокси, например `xray.exe` / `sing-box.exe →
  203.0.113.10:2052`. Оба потока реальны: вместе они показывают, кто что запросил и как трафик
  покинул машину.
* **PTR бесполезен** для фиктивных адресов: обратной зоны нет, а пул переиспользуется.
* **DNS-Client ETW восстанавливает имена.** Вызов резолвера приложением (событие 3008) содержит
  полученный ответ — фиктивный IP. netattrib хранит его с ключом `(ip, pid)`, поэтому следующее
  соединение получает домен, который запросило приложение: `domain: example.com,
  domain_source: dns-client` для `remote_ip: 198.18.0.17`. Более новый ответ для того же IP и PID
  заменяет старый — это следует за переиспользованием пула прокси.

```powershell
netattrib -e winword --dns-events          # строки dns с ответами 198.18.x.x, затем соответствующие соединения
netattrib --group                          # DESTINATIONS: для приложений — домены; для xray/sing-box — прокси-сервер
```

Без ETW (без прав администратора) доступен только PTR, поэтому для fake-IP домен не показывается.

## 8. Формат записей (`--json-lines`)

CSV содержит те же поля в том же порядке с тремя отличиями: `proto` объединяет версию IP (`TCP4`
`TCP6` `UDP4` `UDP6` `DNS`), а `ip_version`, `session_id` и поля только для DNS опущены.

| Поле | Пример | Примечание |
|---|---|---|
| `ts` | `2026-10-21T14:03:22.123456Z` | UTC, время события (метка ETW или время опроса) |
| `event` | `open` | `open` `state` `close` `listen` `dns` |
| `pid`, `ppid`, `session_id` | `4512`, `1200`, `1` | |
| `process`, `path` | `WINWORD.EXE`, `C:\Program Files\…\WINWORD.EXE` | `path` — null, если не определить |
| `user`, `sid` | `CONTOSO\alice`, `S-1-5-21-…` | null при отказе в доступе |
| `sha256` | | с `--hash`, когда вычислен |
| `services` | `Dnscache` | службы внутри svchost с этим PID |
| `proto`, `ip_version` | `TCP`, `4` | `DNS` для записей dns |
| `local_ip`, `local_port`, `remote_ip`, `remote_port` | | IPv4-mapped IPv6 приводится к IPv4 |
| `domain`, `domain_source` | `ecs.office.com`, `dns-client` | `dns-client` (имя, запрошенное приложением) или `ptr` |
| `state`, `direction` | `ESTABLISHED`, `out` | `direction`: `out` `in` `?` |
| `bytes_sent`, `bytes_recv`, `retransmits` | | режим ETW; накопленные на момент записи |
| `duration_ms` | | записи close: время жизни соединения |
| `source` | `etw` | `etw` — сокет видел ETW (включая подтверждённые после опроса, §7.5); `poll` — только опрос; `snapshot` — существовал до запуска |
| `attribution` | `exact` | `exact` `inferred` `exited` (§7.1) |
| `reason` | `disconnect` | записи close |
| `dns_status`, `answers` | `0`, `["13.107.42.14"]` | только записи dns |

Агрегаты и сводка (`--group` с форматом экспорта, `--summary`): `process`, `path`, `user`, `sha256`,
`pids[]`, `active`, `connections`, `tcp`, `udp`, `bytes_sent`, `bytes_recv`, `unique_remotes`,
`first_seen`, `last_seen`, `remotes[]` (`ip`, `domain`, `last_port`, `connections`, байты,
`last_seen`) и `dns_queries[]` (`name`, `count`).

## 9. Сравнение с существующими инструментами

| Инструмент | Механизм | Кратковременные процессы и сокеты | Итог |
|---|---|---|---|
| **Sysinternals TCPView / Tcpvcon** | Опрос `GetExtendedTcpTable`/`UdpTable` по таймеру (1/2/5 с) | Слабо: соединение между двумя обновлениями не появится; завершившийся процесс показывается как `<non-existent>`; PID не привязан к экземпляру | Быстрый интерактивный взгляд на долгие соединения; не журнал аудита |

| **Аудит WFP** (события 5156/5157) | Встроенный событийный аудит | Да | Чрезвычайно шумный, без байтов |

|---|---|---|

| Байты | Нет | Размеры каждой отправки и приёма |

| Стоимость | Постоянная, пропорциональна размеру таблиц × частоте | Пропорциональна трафику; нужны фильтрация в ядре и быстрый потребитель |

Подходы дополняют друг друга, поэтому netattrib использует оба.

## 11. Известные ограничения

* **DNS в обход резолвера Windows** (DNS-over-HTTPS, встроенные резолверы браузеров) не порождает
  событий DNS-Client; для таких потоков остаётся PTR, часто имена CDN.
* **QUIC/HTTP3** виден как потоки UDP (закрываются после `--udp-idle`, по умолчанию 60 с), без
  состояния TCP.
* **Прокси и виртуальные машины:** трафик приписывается процессу-владельцу *сокета*. Какое
  приложение породило какое исходящее соединение прокси, по данным сокетов не установить. Трафик
  гостевых систем WSL/Hyper-V виден под `vmmem`/`vmcompute`.
* **Байты** есть только в режиме ETW и только с момента начала наблюдения.
* **Несколько служб в одном svchost** делят PID; `services` перечисляет все.
* Loopback исключается только в нефильтрованных консольных режимах без `--include-loopback`; GUI и
  любой запуск с `--filter-exe/-pid/-path` его включают.
* **Проверка подписей офлайн:** отзыв сертификатов не проверяется. Подписи проверяются только в
  GUI; в консольном выводе полей подписи нет.
* **Close Connection** работает только для IPv4 TCP, и приложение может сразу переподключиться.
